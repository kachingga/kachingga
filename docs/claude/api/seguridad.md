# Seguridad de la API: cómo está implementada

> **Aplica a:** `apps/api/src/index.ts`, `apps/api/src/trpc/context.ts`, `apps/api/src/lib/session.ts`, `apps/api/src/trpc/init.ts`, `apps/api/src/lib/access.ts`, `apps/api/src/lib/rateLimit.ts`, `apps/api/src/lib/quotas.ts`, `apps/api/src/lib/dbSize.ts`, CORS, RLS. **Si cambiás cómo funciona algo de esto, actualizá este archivo en el mismo PR.** Las reglas generales están en el `CLAUDE.md` raíz → "Seguridad" y el checklist por procedure en `apps/api/CLAUDE.md`.

| Capa | Cómo | Dónde |
|------|------|-------|
| **Autenticación** | Cada pedido trae `Authorization: Bearer <token de Supabase>`; `createContext` lo valida con Supabase. Sin token válido: `ctx.user = null`. Si Supabase Auth no responde (red o 5xx): `ctx.authUnavailable`. Con un token válido, también cuándo se inició la sesión con la contraseña o con Google (`ctx.signedInAt`: ver "Volver a identificarse") | `trpc/context.ts`, `lib/session.ts` |
| **Login obligatorio** | Todo es `protectedProcedure` (→ `UNAUTHORIZED`) salvo `health.ping`. Con Supabase Auth caído → `SERVICE_UNAVAILABLE` (503): la sesión puede estar bien, así que no es `UNAUTHORIZED` | `trpc/init.ts` |
| **Autorización por grupo** | `requireMembership` (leer) / `requireActiveGroup` (escribir) al principio de cada procedure; `assertParticipantsInGroup` para ids que vienen en el input. No miembro → `NOT_FOUND` (no revela que el grupo existe) | `lib/access.ts` |
| **Datos personales** | Perfil, alias (de la cuenta y por grupo, solo el propio: nadie le carga alias a otro ni a alguien sin cuenta) y filtros guardados: siempre filtrados por `ctx.user.id`. Borrar la cuenta (`profile.deleteAccount`) no tiene input: siempre es la del que llama, y pide haber vuelto a identificarse (ver "Volver a identificarse"). **El id de cuenta (Supabase) de alguien no le llega a otro:** grupos, participantes, gastos y pagos se devuelven con `select` explícito, sin `userId` ni `createdById` (de un participante, `hasAccount` / `isMe`). Lo controla `accountIds.test.ts`, con todos los procedures | routers `profile`, `participants`, `savedFilters`, `groups`, `expenses`, `settlements` |
| **Validación** | Todo input con Zod (tipos, largos, montos, formato del alias) | `schemas.ts` |
| **Límite de pedidos** | Por IP: global 300/min; códigos de invitación (`groups.preview` / `join`) 20 cada 10 min; `expenses.export` 20/min; `expenses.summary`, `balances.get` y `categories.suggest` 60/min; `profile.deleteAccount` 5 cada 10 min (llama a la API de admin de Supabase). Por usuario: toda mutation, 30/min y 300/hora; códigos de invitación, 20 cada 10 min, y las lecturas caras (`expenses.export`, `expenses.summary`, `balances.get`, `categories.suggest`), lo mismo que por IP (cambiar de red no da más); 200 cosas nuevas por día; pocas lecturas pesadas a la vez (ver "Límites contra abuso"). Excedido → `TOO_MANY_REQUESTS`. Lo de IP corre en un middleware de Hono **antes** de tRPC (un 429 no llama a Supabase); lo de usuario, después del login | `lib/rateLimit.ts`, `index.ts`, `protectedProcedure` en `trpc/init.ts` |
| **Tamaño, topes y cupos** | Pedido de hasta 1 MB, topes en todos los inputs y cupos por usuario / grupo: ver "Límites contra abuso" (abajo) | `index.ts`, `schemas.ts`, `lib/quotas.ts` |
| **Base de datos** | RLS sin políticas en todas las tablas: la API REST de Supabase no ve nada con la clave pública. La API entra como `postgres` | migraciones |
| **CORS** | Solo los orígenes de `CORS_ORIGINS` (el front web). En local no interviene (proxy de Vite) | `index.ts` |
| **Errores** | Mensajes en español sin datos internos: el `errorFormatter` reemplaza por "Error interno. Intentá de nuevo." el texto de **cualquier** error inesperado (lo que tRPC envuelve como `INTERNAL_SERVER_ERROR` con el mensaje original: Prisma, un bug, Supabase…; un `INTERNAL` que tiramos con mensaje propio lo conserva) y a un input inválido le pone su primer problema (no el JSON de Zod). `NODE_ENV=production` en Railway para no devolver stack traces | `trpc/init.ts`, Railway |
| **Secretos** | Solo en `.env` / `.env.prod` (gitignoreados) y en Railway. GitHub tiene escaneo de secretos y bloquea el push si detecta uno | repo |

## Volver a identificarse (borrar la cuenta)

`profile.deleteAccount` no se conforma con una sesión abierta (un celu prestado, un token robado): la persona tiene que haber **iniciado la sesión con la contraseña o con Google hace 5 minutos o menos** (`RECENT_SIGN_IN_SECONDS` en `lib/session.ts`). Si no, `FORBIDDEN`. La web vuelve a iniciar sesión justo antes (`docs/claude/web/usar-la-api.md` → "Borrar mi cuenta").

- **De dónde sale:** el token de Supabase trae el claim `amr`, una entrada por método con el que se inició **esa sesión** y cuándo (`[{ method: 'password', timestamp }]`). Volver a entrar (`signInWithPassword`, Google) crea una sesión nueva con el momento de ahora; **renovar el token no lo cambia** (verificado en el código de Supabase Auth, que escribe las entradas solo al crear la sesión, y contra `stg` el 11/11/2026: después de renovar, el `amr` sigue con el momento del login y solo cambia el `iat`; al volver a entrar con la contraseña, sesión nueva con el momento nuevo). `createContext` lo lee con `signedInAt(token)` (`lib/session.ts`) **después** de que `getUser` validó el token, y lo deja en `ctx.signedInAt`.
- **Solo cuentan `password` y `oauth`** (Google). No los links de los mails (`otp`, `recovery`, `email_change`…): el del mail de "¿Olvidaste tu contraseña?" ya deja elegir otra contraseña, y la regla es contraseña o Google.
- **Por qué no `reauthenticate()` de Supabase:** manda un código por mail que solo sirve para cambiar la contraseña (`updateUser({ password, nonce })`); la API no tiene cómo comprobarlo para otra cosa.
- **Límite de Google:** en un celu prestado con la sesión de Google abierta, volver a entrar con Google es un toque (Google no tiene `prompt=login`; la web pide `prompt=select_account`, que al menos muestra el selector de cuentas). Contra un token robado sí sirve: hace falta la cuenta de Google.
- Tests: `session.test.ts` (leer el `amr`), `http.test.ts` (solo de un token validado) y `deleteAccount.test.ts` (sesión vieja o sin contraseña / Google → rechazado sin tocar nada; recién iniciada → borra). En los tests de integración, `signedInCaller(userId, signedInAt?)` arma un caller con la sesión recién iniciada.

## Límites del rate limiting

- Es **en memoria**: sirve con **una sola instancia** de la API (Railway Hobby). Con varias instancias hace falta un store compartido (ej. Redis).
- La IP sale del **último** valor de `X-Forwarded-For` (el que agrega el proxy de Railway; los anteriores los puede inventar el cliente). **Verificar en el primer deploy** que Railway lo setea así (ver `DEPLOY.md`).
- **IPv6 se agrupa por /64** (`clientIp`): un cliente suele tener un /64 entero y podría ir cambiando de dirección para esquivar el límite.
- Lo de IP cuenta **cada procedure** de un pedido batcheado, con el path leído **igual que tRPC** (adaptador fetch: una barra menos en cada punta, decodificado y separado por comas solo si es batch): `groups%2Epreview` y `groups.preview` con una barra al final cuentan como `groups.preview`. Si alguno se pasa, se rechaza el pedido entero, con la misma forma de error que tRPC (uno por llamada) para que la web muestre el mensaje.
- **Falla cerrado:** si algún path del pedido no es un procedure real (`appRouter._def.procedures`), se responde `NOT_FOUND` ahí mismo (igual cuenta para el límite global), sin llegar a tRPC ni a Supabase. Así, todo lo que corre tRPC se contó con el nombre del procedure que corre. Las reglas se buscan con `Object.hasOwn` (un path como `constructor` no es una regla).
- Los callers de los tests y del seed (sin `ctx.ip`) no tienen límites por usuario; con `caller(userId, ip)` sí. La guardia de tamaño de la base (`MAX_DB_MB`) vale para todos.
- Se reinicia al reiniciar la API, el tope diario de cosas nuevas incluido (aceptable).
- **Memoria acotada:** las claves vencidas se limpian como mucho cada 10 s (`PRUNE_INTERVAL_MS`: la limpieza recorre todo el mapa, nunca en cada pedido) y cada limitador guarda hasta 50.000 claves (`MAX_KEYS`, ~13 MB). Lleno de claves vivas, se van las más viejas de a un décimo (de a una, en Bun cada clave nueva volvía a recorrer las borradas). Una clave desalojada vuelve a contar de cero: para desalojar la de alguien hacen falta decenas de miles de IPs (o cuentas) nuevas dentro de su ventana, que igual tienen cada una su límite. Rechazar claves nuevas, en cambio, dejaría afuera a todos los demás.

## Límites contra abuso

Para que nadie que se registre (o un miembro) llene la base (Supabase Free: 500 MB sumando prod y staging; si se pasa, **la app deja de andar para todos**: `INFRA.md` → "Plan de Supabase") ni trabe la API (un solo proceso de Bun).

| Qué | Cómo | Dónde |
|-----|------|-------|
| **Tamaño del pedido** | Hasta 1 MB (`MAX_BODY_BYTES`). Más → `PAYLOAD_TOO_LARGE` (413) antes de que tRPC lo lea | `index.ts` (`bodyLimit` de Hono) |
| **Topes en los inputs** | Ids ≤ 40 caracteres (`id`); listas ≤ 100 (personas de la división, `categoryIds`); fechas entre 2000 y 2100; código de invitación de 8 caracteres; textos con su largo máximo. Los filtros guardados se guardan como los parseó `expenseFilters` (solo campos conocidos, con sus topes), nunca el JSON que llegó | `schemas.ts`, routers |
| **Cupos** (regla de negocio, `CLAUDE.md` raíz) | 50 grupos creados por usuario (archivados incluidos), 25 personas por grupo (los que ya tenían más siguen andando), 50 categorías por grupo (archivadas incluidas), 30 filtros guardados por usuario y grupo, 5.000 gastos y 5.000 pagos por grupo (borrados incluidos: igual ocupan lugar) → `BAD_REQUEST` con el mensaje. Se cuentan antes de crear: pedidos al mismo tiempo pueden pasarse un poco (uno por pedido simultáneo; los acotan los límites por usuario). No importa | `lib/quotas.ts` |
| **Escrituras por usuario** | Toda mutation: 30/min y 300/hora. Acota qué tan rápido una cuenta puede llenar la base; cuánto, lo acotan los cupos | `USER_WRITE_RULES` en `lib/rateLimit.ts` |
| **Cosas nuevas por usuario** | 200 por día entre todas las mutations que crean filas (`CREATING_PROCEDURES`: grupos, unirse —siempre, también reclamando—, personas, categorías, gastos, pagos y filtros guardados) → `TOO_MANY_REQUESTS` "Llegaste al máximo de cosas nuevas por hoy…". Ventana fija de 24 h desde la primera; cuenta los intentos. Una mutation nueva que crea filas se suma ahí | `USER_CREATION_RULE` en `lib/rateLimit.ts` |
| **Lecturas caras** | `balances.get`, `expenses.summary` y `expenses.export` con límite propio por IP y por usuario. `minimizeTransfers` ordena una sola vez (antes reordenaba en cada vuelta: con miles de personas bloqueaba la API). Con un grupo lleno (5.000 gastos entre 25 personas, medido con PGlite): `groups.list` suma mis saldos en SQL (~20 ms; antes traía cada parte de cada grupo, ~260 ms); `expenses.export` lee de a 500 gastos (`EXPORT_BATCH`: ~4,5 MB de objetos por tanda en vez de ~44 MB de una) y solo guarda el archivo que arma (CSV ~2,2 MB, JSON ~6,2 MB); `expenses.summary` y `balances.get` también suman en SQL (~150 y ~170 ms; antes traían cada parte, ~250 y ~400 ms) | `lib/rateLimit.ts`, `lib/balances.ts`, `lib/aggregates.ts`, `routers/expenses.ts` |
| **Lecturas pesadas a la vez** | `HEAVY_READS` (`expenses.export`, `expenses.summary`, `balances.get`): como mucho 2 a la vez por usuario y 4 en total (`ConcurrencyLimiter`), para que no se lleven el proceso de la API ni las conexiones a la base. Una más → `TOO_MANY_REQUESTS` en el acto, sin cola ("Hay muchas consultas pesadas en curso…"): la web reintenta sola las queries (3 veces, `api-provider.tsx`). El lugar se devuelve al terminar, también con error. Solo pedidos HTTP reales (`ctx.ip`), como los demás límites por usuario. Si se llenan los 4 (no los 2 de una persona), avisa a Sentry, una vez cada 10 min como mucho (`docs/claude/repo/monitoreo.md`) | `HEAVY_READS` y `ConcurrencyLimiter` en `lib/rateLimit.ts`, `protectedProcedure` en `trpc/init.ts` |
| **Tamaño de la base** | Los cupos no impiden que muchas cuentas o grupos la llenen de a poco: el backup diario mide `pg_database_size` de prod y falla (mail de GitHub) si pasa los 350 MB. Qué hacer si salta: `DEPLOY.md` → "Monitoreo" | `.github/workflows/backup.yml` |
| **Guardia de tamaño** (`MAX_DB_MB`) | Con la variable (valores por entorno: `INFRA.md`), la API lee `pg_database_size` cada 10 min como mucho y, mientras la base la pase, rechaza las `CREATING_PROCEDURES` (`SERVICE_UNAVAILABLE`, "Kachingga no puede guardar más cosas por ahora…") y lo avisa a Sentry (una vez por lectura). Editar, borrar y leer siguen andando. Sin la variable (local, tests, CI): sin guardia | `lib/dbSize.ts`, `protectedProcedure` en `trpc/init.ts` |
| **CSV del export** | Una celda de texto que empieza con `=`, `+`, `-`, `@`, tab o CR lleva `'` adelante: nadie mete una fórmula en la planilla de otro | `csvCell` en `lib/exportExpenses.ts` |
| **Carreras** | Nombre de categoría: índice único parcial `Category_active_name_key` (`groupId`, `lower(name)`, solo activas), además del chequeo previo. Archivar la última activa: transacción que bloquea (`FOR UPDATE`) las activas del grupo. Quitar a alguien: `deleteMany` con `userId: null` (si lo reclamaron en el medio, no se borra) | migración `nombre_de_categoria_unico`, `routers/categories.ts`, `routers/participants.ts` |

- El índice parcial **no se puede escribir en el schema de Prisma**: está solo en la migración. `prisma migrate diff` lo ignora (ni el CI "Migraciones al día" ni `db:migrate:new` lo ven como diferencia). No sacarlo.
- Un "update condicional" solo no alcanza para "la última activa": con `READ COMMITTED`, dos archivados a la vez ven cada uno a la otra como activa. Por eso el `FOR UPDATE`.

## RLS

Supabase expone el schema `public` por su API REST y la clave publishable está en la app: **RLS sin políticas** en todas las tablas bloquea esa API. Nuestra API entra como `postgres` y no le afecta. Verificado: la REST devuelve `[]` aunque haya datos. Toda tabla nueva lleva `ENABLE ROW LEVEL SECURITY` (lo agrega `db:migrate:new`). El CI lo controla: el job "Migraciones al día con el schema" (`.github/workflows/ci.yml`) falla si una tabla de `public` queda sin RLS.
