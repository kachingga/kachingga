# Cómo usa la web la API — web

> **Aplica a:** pantallas que piden o mandan datos, `src/lib/trpc.ts`, `src/lib/auth.ts`, login y sesión, tipo de cambio (`src/lib/use-exchange-rate.ts`, `src/components/exchange-rate-fields.tsx`), monedas, alias, export, errores. **Si cambiás cómo funciona algo de esto, actualizá este archivo en el mismo PR.** Reglas cortas: `apps/web/CLAUDE.md`. Cache, optimistic y precarga: `datos-y-cache.md`.

La API ya implementa **toda la lógica de la v1** (permisos, divisiones, redondeo, monedas, saldos, transferencias, totales, export). **La web no recalcula nada de eso**: pide los datos ya resueltos y los muestra.

## Patrones

```tsx
import type { AppRouter } from '@kachingga/api';
import { expenseInput, type ExpenseInput } from '@kachingga/api/schemas';
import { useInfiniteQuery, useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import type { inferRouterOutputs } from '@trpc/server';
import { useTRPC } from '@/lib/trpc';

type Balances = inferRouterOutputs<AppRouter>['balances']['get'];

const trpc = useTRPC();
const queryClient = useQueryClient();

const group = useQuery(trpc.groups.get.queryOptions({ groupId }));

// Lista paginada (expenses.list devuelve { items, nextCursor }; el cursor lo maneja tRPC)
const expenses = useInfiniteQuery(
  trpc.expenses.list.infiniteQueryOptions({ groupId, filters }, { getNextPageParam: (last) => last.nextCursor }),
);

const createExpense = useMutation(
  trpc.expenses.create.mutationOptions({
    onSuccess: () => {
      queryClient.invalidateQueries(trpc.expenses.pathFilter());
      queryClient.invalidateQueries(trpc.balances.get.queryFilter({ groupId }));
    },
  }),
);
```

## Cada cosa

- **Tipo de cambio:** resuelto en `useExchangeRate` + `<ExchangeRateFields>`, que usan el formulario de gasto y el de pago. Al cargar un gasto o pago en otra moneda se precarga la sugerencia de `rates.get({ currency, source })` (`mid`), editable, y se manda el valor final como `exchangeRate`. En **USD**: **Blue** (default) / **Oficial** / **A mano**; en **EUR, BRL, UYU y CLP**: **Oficial** (default) / **A mano**. `rates.get` da 1 unidad en ARS: si la base del grupo es la moneda extranjera y el gasto es en ARS, se muestra "1 USD = X ARS" y se guarda `1 / X`. Entre dos monedas extranjeras no hay sugerencia: solo a mano. También "mantener moneda" (`keepCurrency: true`). Si la cotización no cargó, no se deja guardar. Cada gasto elige lo suyo.
- **Categorías:** son **de cada grupo** (`categories.list`: todas, con `archived` y `expenseCount`). Cada gasto trae `category { id, name, icon, color }`: mostrar siempre esos datos, nunca una lista fija. El formulario de gasto ofrece las activas (y la que ya tenía, aunque esté archivada) con `<CategoryPicker>`; sin elegir manda nada y la API usa "Otros". **Categoría sugerida:** mientras no se elija una a mano (y no al editar), el formulario pide `categories.suggest` con la descripción **con debounce** (`useDebouncedValue`, 400 ms) y `placeholderData: keepPreviousData` (sin volver a "Otros" entre una sugerencia y la siguiente), y la muestra elegida con la marca "Sugerida"; si falla, se ignora. `gcTime` corto para que no se acumule en la cache offline. Los filtros usan `categoryIds`. La pantalla `/grupos/:id/categorias` (`routes/groups/categories.tsx`, desde el menú del grupo y "Editar categorías" del formulario) crea, edita (`<CategoryEditor>`: nombre, ícono y color) y archiva / desarchiva; después de cambiar una, invalidar `categories` y `expenses` (el nombre, ícono y color se ven en los gastos).
- **Monedas:** los selectores muestran **todas** las de `currencies` de `@kachingga/api/schemas`, con su nombre en español (`currencyLabels` en `src/lib/format.ts`). Nunca una lista a mano.
- **Alias para cobrar:** `groups.get` trae el de cada participante (`paymentAlias`, `paymentAliasSource`). "Copiar alias" y "Copiar monto" (`formatPlainAmount`).
- **Copiar y compartir** (`src/lib/share.ts`): todo lo que se copia pasa por `copyText`, que avisa con un toast (en el celu no hay otra señal). El código de invitación se comparte con `shareInviteCode` (menú de compartir del celu, `navigator.share`) con un link a `/grupos/unirme?codigo=…` que abre "Unirme" con el código ya buscado; donde no se puede compartir, lo copia.
- **Mis grupos:** `groups.list` trae `myBalanceCents` (mi saldo en la moneda base de cada grupo); se muestra con `formatMyBalance`, igual que en el grupo.
- **Borrar mi cuenta** (pantalla `/cuenta/borrar`, `src/routes/delete-account.tsx`; Mi cuenta solo linkea): pide `groups.list({ includeArchived: true })` al abrir (`useQuery`, se vuelve a pedir al entrar: saldos frescos) y muestra con qué cuenta (`email`), mi nombre (`myName`) y lo que dejo pendiente en cada grupo (`myBalances`, ya calculado por la API). Abajo, **"Confirmá que sos vos"**, porque la API solo borra si la sesión se inició con la contraseña o con Google hace 5 minutos o menos (`docs/claude/api/seguridad.md` → "Volver a identificarse"):
  - **Contraseña** (si la cuenta tiene la identidad `email` en `user.identities`, o no tiene Google): `signIn(email, contraseña, captcha)`, que crea una sesión nueva, y enseguida `profile.deleteAccount`. Lleva captcha como el login (`useCaptcha`, uno nuevo después de cada intento). `invalid_credentials` → "La contraseña no es correcta.".
  - **Google** (si tiene la identidad `google`): "Confirmar con Google" → `reauthenticateWithGoogle()` (como `signInWithGoogle`, con `prompt=select_account`: siempre muestra el selector de cuentas de Google) con la vuelta guardada en `/cuenta/borrar?con=google` (`rememberReturnToForGoogle`). Con esa marca, la pantalla dice "Ya confirmaste con Google" y borra con un toque más (no lo hace sola: si se eligió otra cuenta de Google, el email de arriba lo muestra). Si la API responde `FORBIDDEN` (tardó más de 5 minutos o la marca se escribió a mano), saca la marca y vuelve a pedir que confirme. Ir a Google para volver a `/grupos` borra un destino guardado que quedó de un viaje a Google sin vuelta, así no aparece esta pantalla en el próximo login.
  - Las cuentas con las dos identidades ven las dos opciones; quien entró con Google y después cambió el email tiene `email` pero no contraseña: usa Google.
  - Después: `useSignOut()` (igual que "Cerrar sesión") → toast "Tu cuenta se borró". Si falla, toast con el error e invalida todo (la API ya pudo desvincularlo de sus grupos; reintentar termina, volviendo a confirmar). **Probado contra Supabase real** (stg, desde staging, 10/11/2026, con una cuenta de email y contraseña): después de borrar, el token que ya tenía la sesión da 401 en la API y no se puede volver a entrar ("El email o la contraseña no son correctos"); Supabase borra la contraseña y los metadatos y reemplaza el email por un hash (en `auth.users` y `auth.identities`), así que el email queda libre para registrarse de nuevo; y `useSignOut()` con la cuenta ya borrada igual cierra la sesión local (vuelve a `/login`). Falta probarlo con una cuenta de Google.
- **Grupo archivado:** se puede ver pero no modificar. Las pantallas del grupo esconden lo que escribe y muestran `<ArchivedNotice>` (con "Desarchivar"); la API lo rechaza igual.
- **Filtros:** viven en la URL (`src/lib/url-filters.ts`: `readUrlFilters` / `writeUrlFilters`, con días y montos como los muestran los campos) y `toApiFilters` los pasa a lo que toma la API (`Date`, centavos). Así no se pierden al abrir un gasto y volver. Las listas paginadas cargan la página siguiente al llegar al final (`<LoadMore>`).
- **Exportar:** `expenses.export` devuelve `{ filename, mimeType, content }` → `new Blob([content], { type: mimeType })` + un `<a download={filename}>`.
- **Fechas** viajan como `Date` (superjson). La de un gasto o pago es un día del calendario: ver `plata-y-fechas.md`.
- **Errores:** los `TRPCClientError` traen `message` en español listo para mostrar (`ErrorState` en queries, toast en mutations). `NOT_FOUND` en un grupo = no sos miembro. `TOO_MANY_REQUESTS` = límite de pedidos: mostrar el mensaje y no reintentar en loop.
- **Si a la web le falta algo de la API**, se agrega en `apps/api` (mismo repo), nunca workarounds en el front.

## Login (Supabase Auth: email + password y Google)

- **Decisión:** el login va **directo contra Supabase** (`src/lib/auth.ts`), no por nuestra API; la librería guarda la sesión (localStorage) y **renueva el token** sola. Los datos siempre por la API.
- **Google** (`signInWithGoogle` en `src/lib/auth.ts`, botón `src/components/google-sign-in.tsx` en login y registro): la app se va a Google y vuelve a `/` con un código de un solo uso (flujo **PKCE**, `flowType: 'pkce'` en `src/lib/supabase.ts`); la librería lo canjea por la sesión al cargar, así que `useSession()` ya la ve y `/` manda a `/grupos`. La URL de vuelta tiene que estar permitida en Supabase (`INFRA.md` → "Supabase"). **iPhone con la app instalada:** el ida y vuelta a Google puede abrirse en Safari en vez de la app (y la sesión quedar en Safari); se verifica en #42.
- `src/lib/trpc.ts` manda el token en cada pedido (`Authorization: Bearer`). Sin sesión, todo menos `health.ping` responde `UNAUTHORIZED`. `src/components/api-provider.tsx` reintenta una vez un `UNAUTHORIZED` (carrera justo después del login). `SERVICE_UNAVAILABLE` (503) = Supabase Auth no respondió: la sesión puede estar bien, así que nunca es motivo para cerrarla (se reintenta como cualquier error). La sesión la decide solo Supabase en la web (`useSession`), nunca un error de la API.
- **Volver a donde iba después de loguearse** (`src/lib/return-to.ts`): una página privada abierta sin sesión (ej. el link de invitación `/grupos/unirme?codigo=…`) manda a `/login?volver=<esa página>`; login y registro vuelven ahí (y el link entre login y registro lo conserva). Google sale de la app y vuelve a `/`, así que el destino se guarda en `sessionStorage` antes de ir y `/` (`src/components/after-google.tsx`) sigue hasta ahí. Solo se aceptan rutas de la app (`safeReturnTo`): nunca otro sitio.
- **Confirmar el email** (cuando *Confirm email* está prendido en Supabase; antes de eso, todo sigue igual): `signUp` manda `emailRedirectTo` = `/login?volver=…` y, sin sesión en la respuesta, el registro muestra "Revisá tu mail" (`ConfirmEmailSent`, `src/components/mail-sent.tsx`) con "Reenviar mail" (`resend`; 60 s entre uno y otro, el límite de Supabase por dirección). El link del mail vuelve a `/login`, que confirma, entra y sigue a `volver`; si venció o ya se usó, lo dice y deja entrar igual. Login con el email sin confirmar (`email_not_confirmed`) → "Confirmá tu email" con "Reenviar mail".
- **¿Olvidaste tu contraseña?** `/recuperar-contrasena` (`src/routes/forgot-password.tsx`) → `resetPasswordForEmail` con `redirectTo` `/nueva-contrasena`. El mensaje es neutro: no dice si la cuenta existe (Supabase tampoco). `/nueva-contrasena` (`src/routes/new-password.tsx`) canjea el link (o usa la sesión, si ya hay) → `updateUser({ password })` → `/grupos`; si el link venció o ya se usó, "Este link ya no sirve" con "Pedir otro link". La sesión queda en el navegador donde se abrió el mail (en el iPhone, Safari: después se entra a la app instalada con la contraseña nueva).
- **Los links de los mails** traen el token en el hash: las plantillas de Supabase arman `{{ .RedirectTo }}#token_hash={{ .TokenHash }}` (`INFRA.md` → "Supabase"), y la pantalla de destino lo canjea con `verifyOtp` y lo saca de la URL (`useEmailLink`, `src/lib/email-link.ts`). **Por qué no el link por defecto** (`{{ .ConfirmationURL }}`): con PKCE vuelve con un `?code=` que solo se puede canjear en el navegador donde se pidió el mail, y en el iPhone la app instalada y Safari (donde abre el link) no comparten nada. El token anda en cualquier navegador y, en el hash, no llega a ningún servidor. Si igual llega un `?code=` (plantilla por defecto), la librería lo canjea al cargar cuando puede. **Ojo al iniciar sesión se remonta toda la app** (`ApiProvider` arma la cache por usuario): por eso el canje se guarda por token y una pantalla montada de nuevo reusa el resultado en vez de canjear dos veces un token de un solo uso (el token sale de la URL pero queda en el `state` de esa entrada del historial, así la pantalla montada de nuevo lo encuentra; solo mientras la página vive: al recargar no se reintenta), y el login con sesión ya iniciada (sin un token por usar) sigue directo a `volver`. `useEmailLink(verify, session)` da solo si anduvo; `useEmailLinkResult`, también lo que respondió Supabase (lo usa "Cambiar email").
  - **Con una sesión ya abierta en ese navegador, el link no se canjea solo:** la pantalla pregunta (`EmailLinkChoice`, `src/components/email-link-choice.tsx`, estado `'ask'`) mostrando con qué cuenta está. "Quedarme en mi cuenta" va a `/grupos` reemplazando la entrada del historial (el token sale sin canjearse); "Seguir con el link" lo canjea como siempre. Mientras la sesión se restaura (`useSession()` = `undefined`), espera. Un token que esta página ya está canjeando no vuelve a preguntar (la pantalla montada de nuevo con la sesión que acaba de abrir el link).
  - **Si el canje inicia sesión**, un toast dice con qué cuenta ("Entraste como …"), una vez por token.
- **Cambiar el email** (Mi cuenta → `EmailCard` en `src/routes/account.tsx`): `requestEmailChange` = `updateUser({ email }, { emailRedirectTo: '/cambiar-email' })`, con la sesión (sin captcha: Supabase no lo pide en `PUT /user`). Antes valida formato (`z.email()`) y que sea distinto del actual (Supabase guarda los emails en minúscula); `email_exists` → "Ya hay otra cuenta con ese email.". Con *Secure email change* prendido, Supabase manda **dos mails con la misma plantilla** (*Change email address*), uno a la dirección actual y otro a la nueva, **cada uno con su propio `{{ .TokenHash }}`** (`{{ .SendingTo }}` dice a cuál va), y cambia el email recién cuando se abrieron los dos. `/cambiar-email` (`src/routes/change-email.tsx`) es **pública** (el mail se puede abrir en Safari sin sesión) y canjea el token con `verifyOtp({ token_hash, type: 'email_change' })` (`useEmailLinkResult`): el **primer** link responde sin usuario ni sesión (Supabase solo dice "confirmá el otro") → "Falta un paso"; el **segundo** cambia el email y responde con sesión (inicia sesión en ese navegador, y la app se remonta) → "Tu email ahora es …"; vencido o ya usado → "Este link ya no sirve". Sin sesión ofrece "Entrar"; con, "Ir a Mi cuenta" (y antes de canjear pregunta si seguir con el link, como en las otras pantallas: un toque más). Sin token → `/cuenta`.
  - **Mientras falta confirmar**, Supabase lo guarda en la sesión (`user.new_email`) y Mi cuenta lo muestra. Como los links se suelen abrir en otro navegador (en el iPhone, Safari), la sesión de la app no se entera hasta renovarse (hasta 1 h): por eso Mi cuenta, con un cambio pendiente y conexión, pide la sesión de nuevo (`refreshSession`) y muestra el email real.
  - **Con *Confirm email* apagado** (*autoconfirm*), Supabase igual manda los dos mails, pero cambia el email con el **primero** que se abra (el otro queda vencido).
  - **Cuentas solo con Google:** también pueden. Al confirmar, Supabase le suma a la cuenta una identidad de email con la dirección nueva y la de Google sigue vinculada; "Continuar con Google" busca la cuenta por la identidad de Google, no por el email, así que sigue entrando a la misma. Contraseña no tienen: si quieren una, "¿Olvidaste tu contraseña?" con el email nuevo.
- **Captcha (Cloudflare Turnstile)** en el login con email, el registro, "¿Olvidaste tu contraseña?" y "Reenviar mail" (Google no lo lleva): `useCaptcha` (`src/lib/use-captcha.tsx`, con `@marsidev/react-turnstile`) da el widget (con el tema claro / oscuro de la app) y el token, que va en `captchaToken` y valida Supabase (Authentication → Attack Protection). El botón espera al token, y después de cada intento se pide otro (`reset()`: son de un solo uso). Sin `VITE_TURNSTILE_SITE_KEY` (tests de Vitest) no hay widget ni token; local, staging y los E2E usan la *site key* de prueba de Cloudflare, que siempre pasa (`INFRA.md` → "Supabase"). La CSP (`servidor-y-headers.md`) permite `https://challenges.cloudflare.com` en `script-src` y `frame-src`.
- **Errores de Supabase:** vienen en inglés; `authErrorMessage` (`src/lib/auth-errors.ts`) traduce los que se pueden ver en estas pantallas por `error.code` (credenciales, email sin confirmar, cuenta que ya existe, contraseña débil, captcha, límites de pedidos, registro cerrado; al cambiar el email, `email_exists` dice "Ya hay otra cuenta con ese email.") y lo demás es un mensaje genérico, nunca el texto crudo.
  - **Registro cerrado** (*Allow new users to sign up* apagado en Supabase, hoy en prod: `INFRA.md` → "Supabase"): `signUp` responde `signup_disabled` → "Por ahora no se pueden crear cuentas nuevas.". Las cuentas que ya existen entran igual.
  - **Google vuelve con un error** (ej. una cuenta nueva con el registro cerrado): Supabase vuelve a `/` con `?error=…&error_code=…` en vez del código, y la librería no inicia sesión. `RequireAuth` lo ve (sin sesión, en `/`) y manda a `/login?google=<error_code o error>`; el login lo muestra con `googleErrorMessage` (`signup_disabled` → "Por ahora no se pueden crear cuentas nuevas."; cualquier otro, "No se pudo entrar con Google…"), nunca el código crudo. Adónde iba sigue guardado para Google (`return-to.ts`).
- **Cerrar sesión** (`useSignOut()` → `signOut` → `signOutOfDevice` en `src/lib/supabase.ts`) **siempre deja el dispositivo sin sesión**: con conexión Supabase la revoca y la librería la borra; sin conexión (o si Supabase no responde con el token vencido) la librería devuelve error y la conserva en `localStorage`, así que se borra igual (la clave de la sesión está fija en `storageKey`, la misma que usaba la librería) y se termina el cierre local (`signOut({ scope: 'local' })`, que dispara `SIGNED_OUT`). Si el navegador dice que no hay conexión ni se intenta (la librería tarda ~25 s en rendirse), y tampoco se espera el cierre local: la librería lo hace recién cuando terminó de arrancar, y recién abierta la app sin red con el token vencido eso es cuando se rinde de renovarlo (~25 s); la sesión ya no está en el dispositivo, `useSignOut` borra la cache y va a /login en el acto, y el `SIGNED_OUT` llega después. Limitación: offline no se revoca en Supabase; el refresh token sigue valiendo hasta que vence, pero ya no está en el dispositivo. Test: `src/lib/__tests__/supabase.test.ts`.
- Las rutas privadas van dentro de `<RequireAuth />` en `src/router.tsx`. `useSession()` devuelve `undefined` mientras restaura la sesión (se muestra el logo, `<Splash>`), `null` sin sesión. Sin conexión y con la cache del último usuario, `ApiProvider` y `RequireAuth` no esperan la sesión: abren en solo lectura (`datos-y-cache.md` → "Offline").
- Después del login: `groups.list`. Unirse: `groups.preview` con el código → elegir participante sin cuenta o nombre nuevo → `groups.join`.

## En local: proxy de Vite

`VITE_API_URL` va **vacía** en local: la web llama a `/trpc` en su mismo origen y Vite (`dev` y `preview`) lo reenvía a la API en `localhost:3000` (`vite.config.ts`). Así no hay CORS y funciona desde un celu en la misma Wi-Fi (`bun run dev:celu` expone la web en la red local con `KACHINGGA_LAN=1` → `server.host`; por defecto solo `localhost`). En staging y prod, `VITE_API_URL` = la API de ese entorno (`https://api-staging.kachingga.com` / `https://api.kachingga.com`) y CORS sí importa (la URL de la web en `CORS_ORIGINS`).
